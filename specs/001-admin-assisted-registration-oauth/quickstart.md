# Quickstart: Validate Admin-Assisted Registration, Google Sign-In, and Auth Polish

**Feature**: `001-admin-assisted-registration-oauth`

This is a validation guide, not an implementation guide. It names the runnable
scenarios that prove the feature works end to end, and where to look when one
fails. Details of ports and DTOs live in
[data-model.md](./data-model.md) and [contracts/](./contracts/).

## Prerequisites

- PostgreSQL reachable; `pnpm prisma:generate` run in `admission-service` and
  `identity-service` (`identity-service` seeds roles and permissions:
  `pnpm seed:iam` or the repo's seed entry).
- Dev servers running: `identity-service` on `:3000`, `academic-service` on
  `:3200`, `admission-service` on `:3700`, `admission-web` on `:5175`.
- An `ADMIN` account (or `SUPER_ADMIN`) and, for Story 2, a Google account whose
  email matches an applicant account.
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` filled in from Google Cloud
  Console, with callback `http://localhost:3000/auth/google/callback`
  registered. These cannot be generated by an agent (FR-024).
- `GOOGLE_OAUTH_SUCCESS_REDIRECT_URL` and the allowlist must include
  `http://localhost:5175` (see [R5](./research.md)).

## Story 1 — Administrator registers and fills the form

Run:

1. Sign in as `ADMIN`; open `/admin/applicants`.
2. Choose "Daftarkan Pendaftar"; fill name / email / phone / wave / password /
   confirmation; submit.
3. Walk the seven steps, uploading one document and a payment proof.
4. Submit; read the completion panel.

Expect:

- Step 2 yields a DRAFT application: `GET /admissions/applications/:id` returns
  `status: "DRAFT"` and the caller's admin identity is untouched.
- Every step write hits `PATCH /admissions/applications/:id/form` (or the upload
  routes) and returns `200`; no request targets `my-application`.
- On submit, `status` becomes `SUBMITTED` and one `STATUS_CHANGE` notification is
  created on the application (`200`/`201`), by the admin's action.
- The completion panel shows registration number, email, password exactly once.

Then sign out and sign in as the created applicant: `/registration` shows the
same application with the documents and payment attached.

Negative checks:

- Register with an email that already exists → `409`, error shown on the email
  field, no second account.
- Register against a closed wave → `400` "wave not found or already closed".
- Stop after step 2 → the DRAFT application appears in `/admin/applicants`
  (visible, repairable).
- Submit with a required document missing → `400` listing the missing item.

## Story 2 — Google sign-in

Run:

1. Sign out; open `/login`. Activate "Masuk dengan Google".
2. Complete the Google screen with the email of an existing applicant.
3. Then repeat with an email that has no account.

Expect:

- Activation issues a full-page navigation to
  `http://localhost:3000/auth/google?redirect=http%3A%2F%2Flocalhost%3A5175`.
- The Google start redirect is issued and the callback returns a `302` to
  `http://localhost:5175/oauth/callback?profileIncomplete=...`.
- On `/oauth/callback` the app calls `POST /auth/refresh` (cookie present) and
  routes to `/registration`; the applicant sees their application.
- Unknown email: the callback still returns a session, but the user has no role,
  so the app shows "account not registered" and links to `/register`. No second
  application exists.
- `redirect` set to an unlisted origin (manually) → the callback falls back to
  the configured default, never to the unlisted origin.
- Stop `identity-service` and activate the control → a service-outage message,
  not "wrong credentials".

## Story 3 — Blank screens

Run:

1. As `ADMIN`, open `/registration` directly, then `/registration/form`.
2. As an applicant with no application (or a roleless Google user), open the
   same two routes.

Expect: each renders an explanatory empty state with a working next action and
no applicant-only write control. No white page. The only console error permitted
is the known `/settings` 404.

## Story 4 — Form polish

Run: open `/register` and `/login`.

Expect:

- `/register` uses the shared floating-label field with per-field messages
  (no manual `validate()` + toast for field errors).
- The password visibility toggle exists on both screens and reports state to
  assistive technology.
- A successful registration shows a dedicated success state with the
  registration number and a link to sign in, replacing the transient toast.
- Tab through both screens: every control is reachable with a visible focus
  indicator.

## Verification commands (run only when asked)

| Repo | Command |
| --- | --- |
| `admission-service` | `pnpm test` then `pnpm run validate` |
| `identity-service` | `pnpm test` then `pnpm run validate` |
| `admission-web` | `pnpm test` then `pnpm run validate` |

Sibling web apps that receive mirrored auth files: `pnpm run validate` in each,
because a mirrored file that fails lint in one repo is a broken shared contract.

## Failure triage

| Symptom | Likely cause |
| --- | --- |
| Callback lands on the wrong app | `GOOGLE_OAUTH_SUCCESS_REDIRECT_URL` / allowlist still says 5173 |
| Google start returns 400 | `redirect` origin not in the allowlist |
| `admissions.create` request returns 403 | Seed not re-run, or permission not added to the catalogue |
| Admin step write returns 404 | Path used is `my-application` instead of `applications/:id` |
| Upload returns 409 | Application not in `DRAFT` / `REVISION_NEEDED` |
| Blank `/registration` still | `v-else` branch missing, or a thrown error before `loading = false` |
